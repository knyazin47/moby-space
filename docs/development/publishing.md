# Публикация Moby Space

Публичный пакет содержит текущие исходники обоих режимов, контракты, тесты,
инструкции, ресурсы с установленными условиями и изображения README.
История разработки и готовые пакеты прежних версий не входят в этот набор.

## 1. Проверить права и авторство

- Согласовать с авторами публикацию их вклада по MIT и проверить условия
  участия в хакатоне. Checkbox в AUTHORS подтверждает участие; сам по себе
  он не заменяет согласие на лицензирование прежнего вклада.
- Сохранить LICENSE, NOTICE, реестры ресурсов и уведомления зависимостей.
  Собственные иллюстрации имеют MIT, шрифты и emoji — свои лицензии.
- Для фотографий проверить разрешение на размещение в README нового
  репозитория. Их отдельное переиспользование требует согласования с автором.
- Для внешнего баннера и логотипов установить основание использования.
  При отсутствии такого основания оставить названия и ссылки на мероприятие.
  Внешний URL не предоставляет лицензию на изображение или товарный знак.

Упоминание Space Hackathon с МТБанком сохраняет контекст работы команды.
Описание проекта не должно создавать впечатление официального приложения банка.

## 2. Зафиксировать исходники

Проверить весь tracked tree: без runtime-конфигурации, реальных профилей,
SQLite, ключей, банковских APK, презентаций и материалов reverse engineering.
Рабочее дерево должно быть чистым, а SHA кандидата — записанным.

```sh
python3 tools/check_repository.py --public
python3 tools/test_build_config.py
python3 tools/assets/test_asset_support.py
python3 tools/check_ios_artifacts.py --self-test
git status --short --branch
```

Дополнительно выполнить сканирование кандидата на секреты: в отчёт
попадают категории и пути, а не найденные значения. Удаление старой истории не отзывает
ранее раскрытые credentials; при подтверждённом раскрытии нужен отзыв у эмитента.

Source CI должен пройти на SHA кандидата: Go vet/race, известные Go-уязвимости,
Flutter analysis и оба режима, генерация контрактов без дрейфа, Go/Dart interop.
Команды и ограничения окружения перечислены в [проверках](testing.md).

## 3. Создать новую историю

Подготовить новый репозиторий с выбранным именем сначала в private.
Перенести проверенное Git-дерево в корневой коммит без родителей: это позволяет
сохранить точные байты файлов без дополнительной локальной копии проекта.
Проверить равенство tree ID исходного кандидата и нового коммита, а также
отсутствие родителей у корневого коммита.

Отправить в новый репозиторий только новую ветку main. Старые refs, теги,
релизы, Actions artifacts и настройки с адресами прежнего API не переносить.
Исключить `push --mirror` и `push --tags` из этого переноса.

Автор импорта описывает перенос снимка исходников. Разделение импорта по
каталогам не доказывает историческое авторство этих каталогов. Совместное
авторство указывать с согласия реальных участников и с их GitHub email.

## 4. Настроить страницу и участие команды

Перенести описание About и темы, проверить README, локальные ссылки,
изображения и LICENSE. Homepage оставлять пустым, если работающего сайта нет.

Сохранить возможность `Create a merge commit`. После открытия публичного
доступа каждый участник делает собственный fork и непустой PR в AUTHORS.
При принятии сохраняется его авторский коммит. Условия учёта и порядок PR
описаны в [CONTRIBUTING](../../CONTRIBUTING.md#подтверждение-участия).

Fork сохраняет копию проекта в профиле участника. Для заметного портфолио
участник может закрепить репозиторий у себя и сослаться на общий проект.
Если проект будет архивироваться, дождаться принятия PR команды: в архиве
новые PR недоступны.

## 5. Проверить сборки и открыть доступ

В новом репозитории выполнить source workflow и общий Android/iOS workflow
на выбранной ветке. Проверить APK, unsigned device IPA, SHA-256 и manifests:
source commit и режим должны соответствовать новому репозиторию.
Старые бинарные пакеты не подтверждают проверку нового snapshot.

Для первого публичного выпуска выбрать следующую версию приложения,
согласовать её с pubspec и тегом. Порядок упаковки и подписей — в
[документации релизов](releases.md). iOS IPA требует собственной Apple identity;
ephemeral Android key не гарантирует обновление прежних установок.

Перед переключением visibility проверить итоговые refs и файлы, результаты CI,
условия ресурсов, описание и отсутствие прежних служебных адресов. Открытие
доступа и выпуск тега выполняются после утверждения готового пакета.
Затем проверить страницу и скачивание пакетов без доступа к private-репозиторию.

## Критерий готовности

Публичный репозиторий имеет новую историю, согласованную лицензию и attribution,
работающие инструкции обоих режимов, зелёный CI и Android/iOS-пакеты,
связанные с опубликованным коммитом. В README прямо обозначены синтетические
данные и границы хакатонного прототипа. Физическая приёмка устройств
оценивается отдельно от source checks и сборки пакетов.
